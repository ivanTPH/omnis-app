# Nonce-based CSP — replacing script-src 'unsafe-inline'/'unsafe-eval' (2026-09-01)

**Goal:** the production CSP's `script-src` included `'unsafe-inline'` and
`'unsafe-eval'`, which meant CSP provided no real defence against inline-
script XSS — directly relevant given the stored-XSS gaps found and fixed in
the 31 Aug manual hardening review (`evidence/phase7-security/
manual-hardening-review.md`, §6 explicitly named this as a gap CSP wasn't
covering). Replaced with a per-request nonce: every inline script must
carry a fresh, unguessable value matching what the CSP header itself
declares, or the browser refuses to run it.

**Status:** implemented, extensively tested locally (dev *and* production
build modes), not yet deployed. Per the task's own instruction, this is
flagged for Ivan's review before it goes near production, and recommended
to deploy at a quiet time with Sentry watched closely afterward.

## What changed

1. **`middleware.ts`** — generates a fresh nonce (`crypto.randomUUID()`,
   base64-encoded, matching Next.js's own documented example) on every
   request, builds the CSP with `script-src 'self' 'nonce-<value>'
   'strict-dynamic'` (plus `'unsafe-eval'` in development only — React
   itself needs eval in dev for reconstructing server error stacks; neither
   React nor Next.js use eval in production), forwards the nonce to the
   page render via an `x-nonce` request header, and sets the CSP as a
   response header.
2. **`next.config.ts`** — removed the static `Content-Security-Policy`
   entry from `securityHeaders` (a build-time-fixed header can't carry a
   per-request nonce, which is the whole reason this moved to middleware).
   Every other header there (HSTS, X-Frame-Options, etc.) is unchanged. The
   separate `/api/resource-file/(.*)` override (frame-ancestors only) is
   also unchanged — untouched by this change either way, see "What was
   deliberately left alone" below.
3. **4 marketing pages** (`app/marketing/{home,beta,features,investors}/
   page.tsx`) — each has one hand-written `<script type="application/
   ld+json">` (JSON-LD structured data). Made each page component `async`,
   read the nonce via `(await headers()).get('x-nonce')`, and added
   `nonce={nonce ?? undefined}` to the script tag. These were the *only*
   raw `<script>` tags anywhere in `app/`/`components/` — confirmed by grep,
   not assumed.

Everything else Next.js itself renders (its own hydration/runtime scripts,
page JS bundles, `next/font` preloads) gets the nonce **automatically** —
this is a documented Next.js App Router feature: it parses the CSP response
header for a `nonce-` token and applies it to every script/style tag it
generates itself. Confirmed this actually happens in this exact Next.js
version (16.3.3) by inspecting the raw response: the `Link: rel=preload`
headers for font/CSS preloads carried the same nonce value as the CSP
header, unprompted by anything in this app's own code.

## Why middleware, not next.config.ts, and why the matcher changed

Nonces only work on **dynamically rendered** pages — a statically
pre-built HTML file has no per-request context to inject a nonce into.
Checked the actual build output (not assumed): every single page in this
app is `ƒ` (dynamic) already, including all 4 marketing pages — the only
`○` (static) routes are `/manifest.webmanifest`, `/robots.txt`,
`/sitemap.xml`, none of which render HTML or scripts. So the "must be
dynamic" requirement was already satisfied app-wide before this change;
nothing needed to be forced into dynamic rendering.

`middleware.ts`'s matcher previously excluded `login`, `marketing`,
`forgot-password`, `reset-password`, `set-password`, `verify-email`,
`accept-invite`, `accept-dpa`, `accept-terms` entirely — meaning middleware
(and therefore any nonce generation living there) never ran for those
pages at all. Since they needed nonces too (the marketing pages' JSON-LD
scripts, specifically), the matcher was broadened to include them, and the
function body now replicates the *auth-check* exclusion itself (a
`PUBLIC_PATHS` list, checked in code) — so **the set of pages that skip
`auth()`'s DPA/terms/role-redirect logic is unchanged**, they just
additionally get a nonce+CSP now, which they didn't get any CSP for at all
before (relying solely on `next.config.ts`'s now-removed static entry).
Non-HTML routes (`api`, `_next/static`, `_next/image`, favicon, sitemap,
robots, llms.txt, Google verification files, opengraph-image,
twitter-image, fonts, static image extensions) remain excluded from the
matcher exactly as before — no change to how those are handled.

### A subtlety worth recording: `auth()`'s own `NextResponse.next()` doesn't carry the nonce

`auth(request, event)` — NextAuth's own middleware wrapper — internally
calls `getSession()` (which decodes and, on every request, re-signs/
refreshes the JWT cookie, including the `sessionsInvalidatedAt` check added
1 Sep) and, if the `authorized()` callback allows the request through,
returns a bare `NextResponse.next()` with no knowledge of any nonce. If
this bare response were used as-is, the `x-nonce` request header would
never reach the page render. The middleware now inspects whether `auth()`'s
response is a redirect (`response.headers.has('location')`) — if so, it's
forwarded as-is (nothing renders for a redirect, so no nonce propagation is
needed, only the CSP response header itself); if not, a **new**
`NextResponse.next({ request: { headers: requestHeadersWithNonce } })` is
built instead, with any `Set-Cookie` headers `auth()` set (the session
refresh) copied across explicitly via `getSetCookie()` so that behaviour
isn't lost. This was traced through `next-auth`'s and `@auth/core`'s actual
source (not assumed) to confirm session-refresh cookies survive this
reconstruction — see the code comments in `middleware.ts` for the specific
mechanism.

## What was deliberately left alone

- **`style-src`** — still `'self' 'unsafe-inline' ...`. Out of scope: the
  task was specifically about `script-src`. Not touched.
- **`/api/resource-file/(.*)`'s CSP override** in `next.config.ts` — this
  route is excluded from middleware's matcher (falls under the `api`
  exclusion, unchanged), so it's entirely unaffected by this change either
  way. It never rendered any inline scripts requiring a nonce (confirmed
  when fixing the stored-XSS gap on this exact route on 31 Aug —
  `buildAiSlidesHtml()`/`buildAiResourceHtml()` produce plain HTML/CSS with
  no `<script>` tags at all), so leaving its existing, working,
  narrowly-scoped `frame-ancestors 'self'` override untouched was the
  lowest-risk choice rather than folding it into the new nonce logic.
- **API routes generally** — after removing the static CSP entry, routes
  middleware doesn't cover (plain JSON API endpoints) have no CSP header at
  all, rather than a static fallback. Deliberate: CSP restricts what a
  rendered HTML *document* can do: a JSON response is never rendered as a
  document with executable inline scripts, so a CSP header there has
  limited practical value, and adding one back introduces a second
  "how do middleware-set and next.config-set CSP headers on the same path
  interact" question with no page actually depending on the answer. Simpler
  to have exactly one CSP source (middleware) for the routes that need one.
- **Prefetch-skip matcher optimisation** — Next.js's own CSP guide suggests
  adding a `missing` clause to the matcher to skip `next/link` background
  prefetch requests (they don't render, so generating a nonce for them is
  wasted work). Not added, to keep this change's surface area as small as
  reasonably possible given its risk profile — worth considering as a
  follow-up, not required for correctness.

## Live testing — this is the part that actually matters

Wrote `scripts/test-csp-nonce.mjs`: a Playwright script that logs into
**11 demo accounts** covering every role (Teacher ×2, SENCO, Head of Year,
Head of Dept, SLT, School Admin, Student, Parent, Teaching Assistant,
Academy/Platform Admin), visits each one's dashboard plus 2–6 representative
deeper pages (including every page known to render a chart —
`CohortInsightsPanel`, `BehaviourTrendChart`/Recharts, SLT/attendance
analytics, `PlatformInsightsPanel`, student grade sparklines), opens the
homework marking view and the AI homework-generator modal, and exercises
the **demo role switcher's real click path** (open panel → click a role →
the actual `recordSignOut()` → `signOut()` → `signIn()` sequence added
1 Sep). Every `console` error matching CSP-violation phrasing and every
`pageerror` event is captured and reported; the script exits non-zero if
any violation is found. Demo accounts are MFA-exempt (by design, documented
in `CLAUDE.md`), so this logs in directly with no OTP step needed.

**Marketing/login pages, unauthenticated:** `/marketing/home`,
`/marketing/features`, `/marketing/beta`, `/marketing/investors`, `/login`
— confirmed via raw `curl` that the CSP header's nonce and the JSON-LD
`<script>` tag's `nonce` attribute match exactly within the same response,
before running the full browser suite.

**Run 1 — dev mode** (`npm run dev`, `NODE_ENV=development`, so
`'unsafe-eval'` present as designed): full suite, all 11 roles, all pages,
homework marking, AI generator modal, demo role switcher →
**0 CSP violations, 0 page errors.**

**Run 2 — production build, wrong port (caught a real methodology bug,
not an app bug):** built with `npm run build` (`output: 'standalone'`),
served via `node .next/standalone/server.js` on port 3001 while the build's
baked-in `NEXTAUTH_URL` was `http://localhost:3000` (from `.env.local`).
Got 4 CSP violations, all `connect-src` blocks on `http://localhost:3000/
hoy/dashboard` — a same-origin-relative-to-nothing fetch that only
happened because the test itself was serving the app on the *wrong port*
relative to what was baked into the build. Diagnosed correctly (not
dismissed): this is exactly the failure mode a *real* mismatched
`NEXTAUTH_URL` vs actual deployed origin would produce, which is a
pre-existing operational concern unrelated to CSP nonces specifically (a
wrong `NEXTAUTH_URL` breaks plenty else besides CSP) — and does not apply
to the real deployment, where `NEXTAUTH_URL` is set to
`https://omnis.education`, matching the actual serving origin exactly.

**Run 3 — production build, correct port:** re-served the identical build
on port 3000 (matching the baked-in `NEXTAUTH_URL`), re-ran the full suite
— **0 CSP violations, 0 page errors.** This is the run that matters: real
production build output, `'unsafe-eval'` genuinely absent from `script-src`
(confirmed directly via `curl -I`, see below), every role, every flow.

**Confirmed via `curl -I` in production mode** — the actual header sent:
```
content-security-policy: default-src 'self'; script-src 'self' 'nonce-<value>' 'strict-dynamic'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com https://cdn.jsdelivr.net; font-src 'self' https://fonts.gstatic.com https://cdn.jsdelivr.net; img-src 'self' data: blob: https:; connect-src 'self' https://*.sentry.io; frame-src 'self' https://docs.google.com https://drive.google.com; frame-ancestors 'none'; base-uri 'self'; form-action 'self'
```
No `'unsafe-inline'`, no `'unsafe-eval'`, in `script-src` — exactly the ask.

## Recommendation

Ivan asked to review this closely before it goes near production, and
suggested deploying at a quiet time with Sentry watched afterward given the
"silently stops working" failure mode CSP misconfiguration can produce.
Agreed — this is genuinely higher-risk than most fixes in this repo's
history, precisely because a missed inline script fails *silently* for a
real user (no visible error, just broken functionality) rather than
throwing something an end-to-end smoke test would obviously catch. The
testing above is thorough (every role, every documented chart-rendering
page, the demo switcher's real click path, dev *and* production build
modes, on the correct port) but "thorough automated testing found nothing"
is not the same guarantee as "nothing can possibly be missed" — recommend:

1. Review this document and the diffs directly before deploying.
2. Deploy at a quiet time, as suggested.
3. Watch Sentry (client-side errors specifically — a blocked script
   wouldn't throw a *caught* exception, but React itself may surface
   hydration/rendering errors downstream of a missing script, the way the
   `[auth][error]` noise showed up clearly in this session's own testing
   the moment something was actually misconfigured) for the first while
   after deploy.
4. If anything real does slip through, the fix is to nonce/relocate the
   specific offending script — never to re-add `'unsafe-inline'`/
   `'unsafe-eval'` back to `script-src` as a quick patch.

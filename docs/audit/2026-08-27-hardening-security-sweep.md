## Export routes — in-tenant auth gap (2 findings, fixed)

1. **`app/api/export/lesson-plan/[lessonId]/route.ts`** and **`app/api/export/homework/[homeworkId]/route.ts`** — both called `requireAuth()` with no role restriction; any authenticated user (including students/parents) could hit either export. The underlying Prisma queries were already correctly `schoolId`-scoped, so this was in-tenant only, not cross-tenant. **Fix:** added `const ALLOWED = ['TEACHER', 'HEAD_OF_DEPT', 'HEAD_OF_YEAR', 'SLT', 'SCHOOL_ADMIN', 'SENCO']`, matching the sibling `class-report` route's exact allowlist, plus the standard `if (!ALLOWED.includes(user.role))` 403 check.

   The other 11 previously-unreviewed export routes checked in this pass were clean (role-gated, `schoolId`-scoped).

## `app/actions/**` — cross-tenant IDOR / unscoped writes (12 findings, fixed)

1. **CRITICAL — `app/actions/homework.ts` `createHomework()`.** No role check at all, and `input.classId`/`input.lessonId` were never verified against the caller's `schoolId` before `prisma.homework.create()` — a caller could create homework against another school's class/lesson. Worse: the fire-and-forget notification block right after does `prisma.enrolment.findMany({ where: { classId: input.classId } })` with no `schoolId` filter and then emails/notifies every real student and parent enrolled in that class — so this wasn't just a data-integrity bug, it was a way to send real email to real people at a school you don't belong to.
   **Fix:** added a staff-role check (`TEACHER, HEAD_OF_DEPT, HEAD_OF_YEAR, SLT, SCHOOL_ADMIN, SENCO`) and a `Promise.all` verifying both `classId` and `lessonId` belong to `schoolId` before any write. The enrolment query is unchanged but is now safe transitively, since `classId` is verified first.

2. **HIGH — `app/actions/homework.ts` `saveIlpEvidenceEntries()` auto-achieve branch.** The per-target loop that auto-transitions an `IlpTarget` to `'achieved'` after 3+ PROGRESS entries did `prisma.ilpTarget.findUnique({ where: { id: targetId } })` and `.update({ where: { id: targetId } })` with no ownership check — `targetId` comes from client-supplied `entries[].ilpTargetId`. **Fix:** switched the lookup to `findFirst` scoped via `ilp: { schoolId }` (IlpTarget has no direct `schoolId` column, only via its parent `IndividualLearningPlan`), and the subsequent update now uses the verified record's own id.

3. **HIGH — `app/actions/homework.ts` `suggestHomeworkGrade()`.** `prisma.submission.findUnique({ where: { id: submissionId } })` had no `schoolId` — would return another school's submission content (including student work) to the AI grading prompt. Sibling function `getSubmissionReadOnly()` already does this correctly. **Fix:** switched to `findFirst` with `schoolId` added to `where`, and `role` destructure widened to also pull `schoolId`.

4. **HIGH — `app/actions/kplan.ts` `upsertKPlan()`.** `prisma.kPlan.upsert({ where: { studentId } })` — `studentId` is the model's only unique key, and the function never checked it belongs to the caller's school. Because `upsert` always finds-or-creates on that key regardless of who "owns" it, a SENCO at School A passing School B's `studentId` would silently overwrite School B's existing KPlan (SEND accommodation notes) with School A's data. **Fix:** added a `prisma.user.findFirst({ where: { id: studentId, schoolId } })` check before the upsert, throwing if the student isn't in the caller's school.

5. **HIGH — `app/actions/year-group-plans.ts` `upsertYearGroupPlan()` update branch.** `if (input.id) { await prisma.yearGroupPlan.update({ where: { id: input.id }, data }) }` — unscoped `where`, and `data` includes `schoolId: user.schoolId`. Passing another school's plan `id` would both edit that school's plan content and re-parent the record to the caller's school. **Fix:** added a `findFirst({ where: { id, schoolId } })` ownership check before the update (matching the file's own `submitForApproval`/`approvePlan`/`deletePlan`, which were already correctly scoped).

6. **MEDIUM — `app/actions/lessons.ts` `addUrlResource()`, `addUploadedResource()`, `addLibraryResource()`.** All three write a `Resource` row stamped with the caller's `schoolId` but pointing (via `lessonId`) at a lesson never checked to belong to that school — so a resource (including uploaded file content / `dataUrl` / `extractedText`) could end up attached to another school's lesson. **Fix:** each now does a `prisma.lesson.findFirst({ where: { id: lessonId, schoolId } })` check before writing.

7. **MEDIUM — `app/actions/rag.ts` `confirmGradePrediction()` (and `upsertTeacherPrediction()`, same shape).** No role check (any authenticated user could confirm/override a grade prediction), and `input.studentId` was never checked against the caller's school before the `teacherPrediction.upsert()` or the `prisma.user.findUnique({ where: { id: input.studentId } })` used to build the HOD notification text. **Fix:** added a `TEACHER_PREDICTION_ROLES` allowlist (teaching staff) to both functions, and both now verify `studentId` belongs to `schoolId` before doing anything else; `confirmGradePrediction()` reuses that verified student record instead of a second unscoped lookup.

8. **MEDIUM — `app/actions/adaptive-learning.ts` `getAdaptiveHomeworkSuggestions()`.** `studentLearningProfile.findUnique({ where: { studentId } })` and `sendStatus.findUnique({ where: { studentId } })` — both keyed only by `studentId`, never checked against `schoolId`. Sibling function `getStudentLearningProfile()` in the same file already does this correctly. **Fix:** added the same `role: 'STUDENT'`-style ownership check before the `Promise.all`.

9. **MEDIUM — `app/actions/homework.ts` `resendHomeworkReminder()`.** `prisma.user.findUnique({ where: { id: studentId } })` — unscoped; the resulting email/notification would go to whatever real user that id resolved to, at any school. **Fix:** scoped to `findFirst({ where: { id: studentId, schoolId } })`, throws if not found.

10. **LOW (dead code, fixed defensively) — `app/actions/adaptive-learning.ts` `getIlpEvidenceDashboard(schoolId)`.** Took `schoolId` as a raw function parameter with zero cross-check against the session — any caller could pass an arbitrary school's id. Currently has no callers in the app, so not reachable today, but it's an exported server action and a UI wire-up would inherit the bug silently. **Fix:** the parameter is now ignored for scoping purposes; `schoolId` is always derived from the authenticated session instead.

11. **LOW — `app/actions/lessons.ts` `createLesson()`.** `input.classId` was written into the new lesson with no check it belongs to the caller's school. **Fix:** added a `schoolClass.findFirst({ where: { id: input.classId, schoolId } })` check when `classId` is provided.

12. **LOW — `app/actions/lessons.ts` `getSchoolResourceLibrary()`.** The optional `forLessonId` contextual lookup (`prisma.lesson.findUnique({ where: { id: forLessonId } })`, used only to derive a `subject` string for filtering) had no `schoolId` — a very weak cross-tenant existence/subject oracle, not a data leak of any real content. **Fix:** scoped to `findFirst` with `schoolId`.

All 24 files listed as "not reached at all" in the 2026-08-26 audit have now been reviewed at least once; the remaining files in that list beyond the 12 above were read and found already correctly scoped.

## This session's own new code — DSPy inputRefs cross-tenant leak (1 HIGH finding, fixed)

**`lib/agents/plan-synthesis.ts`** — the `AgentAuditEntry.inputRefs` populated earlier this session (see `docs/audit/2026-08-27-dspy-agent-skill-optimization.md`, "round 3") for the `APDR_CYCLE` and `SEND_DIFFERENTIATION` skills carried raw free text: ILP target descriptions, K Plan strategy text, and LLM-generated conflict prose explicitly instructed to "cite specific plan elements." This is special-category SEND data (SEND status, support strategies, EHCP/ILP-adjacent content).

The risk isn't the in-app UI — `AiDecisionExplanation.tsx`'s `describeInputRefs()` only ever renders `Object.keys(refs)` (field names), never the values, and the DSAR JSON/PDF exports only expose a student's own `inputRefs` to their own school's admins. The real path is `dspy-service`'s weekly optimizer: it deliberately pools training examples **across all non-demo schools** (a documented design choice, not a bug), and a promoted `AgentSkillVersion.demonstrations` — which is a genuinely global table with no `schoolId` — gets injected verbatim as JSON into every school's live agent system prompt via `resolveSkillFragment()`/`resolveSkillVersion()` (`lib/agents/skill-prompt.ts:78-79`). If DSPy selected an entry containing one school's raw ILP target text as a demonstration example, that text becomes part of the literal system prompt every other school's `plan-synthesis` calls send to the model — a real, if indirect, cross-tenant exposure of one student's SEND data to another school's AI pipeline.

**Fix:** `writeAuditEntries()`'s `push()` calls for both skills now carry only ids and counts:
- `APDR_CYCLE`: `targetsWithoutEvidenceIds` / `missingKPlanCoverageIds` (parallel id arrays added to `PreCheckResult`, computed alongside the existing description arrays) and `staleStrategyCount` (K Plan strategies have no stable id, so only a count is kept — the previous version stored up to 3 raw strategy-text snippets).
- `SEND_DIFFERENTIATION`: `conflictCount` instead of the raw `analysis.conflicts` string array.

The human-readable `outputSummary`/`decision` text this agent writes to its own school's audit trail — and the prompt payload it sends to the LLM for its own school's analysis — are unchanged; only the cross-tenant-pooled `inputRefs` field was narrowed. Anyone with legitimate access to a school's own data can still resolve an id back to the actual target/strategy text within that school's own tenant boundary.

**Not fixed this round, flagged for a future pass:** `evidence-agent.ts`'s `inputRefs` (`targetId`, `submissionId`, `planType` — all ids, no free text) and `coach.ts`/`quality.ts`/`engage.ts`'s `inputRefs` (submission ids, topic strings) were reviewed and are fine as-is — topics are short curriculum-subject strings (e.g. "Photosynthesis"), not personal/special-category data, so they weren't changed.

## Structural note — `ResourceVersion` has no `schoolId` column (not fixed, deferred)

Flagged during this pass, not itself exploitable today: `ResourceVersion` (added in the 2026-08-26/27 DSPy schema work, `resourceId` a loose non-FK reference since `f5e4ff4`) has no `schoolId` column at all. Nothing in the app currently reads `ResourceVersion` rows unscoped — `data.py`'s join and the write sites in `send-support.ts` are all correctly school-scoped upstream — so there's no live vulnerability. But it reproduces the exact bug shape found repeatedly in both this audit and 2026-08-26's: a table storing raw SEND edit-diff text (`ResourceVersion.diffSummary`, via `lib/text-diff.ts`) with no tenant column to check, one query away from a leak if a future reader is added without threading `schoolId` through the `resourceId` join.

**Recommendation, not actioned this round:** add a denormalized `schoolId` column to `ResourceVersion`, populated at write time from the caller's session (both existing write sites — `updateIlpTargetText()`/`updateIlpDraft()` in `send-support.ts` — already have `schoolId` in scope). This is a `schema.prisma` change and, per the process note in the DSPy audit doc, should be made and validated (`npx prisma generate` / `npx prisma validate`) from a real terminal in one sitting rather than through the device bridge, to avoid repeating the `Resource.versions` slip from round 3. Deliberately left as a recommendation rather than done live in this pass.

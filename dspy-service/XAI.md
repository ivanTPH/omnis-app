# XAI: explaining Omnis's AI agents

Companion to DESIGN.md / INTEGRATION.md. Where those cover *improving* the
agents, this covers *explaining* them — for a SENCo who needs to justify a
decision, a parent who asks "why did the AI say this about my child," or a
DPO responding to a subject access request.

This is a documentation and query-pattern spec, not new infrastructure: the
data it explains from already exists (`AgentAuditEntry`, and from now on
`AgentSkillVersion`). What's missing is the *presentation layer* — turning
rows that already exist into an answer a non-technical person can read. That
build is scoped at the end of this doc.

## The legal grounding, briefly

- **UK GDPR Article 22** gives a data subject the right not to be subject to
  a decision based solely on automated processing that produces legal or
  similarly significant effects, and — where automated processing is used
  as part of a decision — a right to meaningful information about the logic
  involved. Omnis's own design already sits on the safe side of this: every
  `AgentAuditEntry` has a `reviewOutcome` field, meaning no AI output reaches
  a student's record un-reviewed by a member of staff. That review step is
  the thing to be able to *prove* happened, not just assert.
- **ICO's "Explaining decisions made with AI" guidance** sets out that a
  good explanation covers: what happened (rationale), what data and logic
  were used (responsibility, data, fairness), and what happens next (safety,
  performance, impact). The query patterns below are structured around
  those categories deliberately.
- **SEND Code of Practice** accountability duties (the graduated approach,
  the assess-plan-do-review cycle) require that decisions about a child's
  support are traceable and reviewable by the people responsible for that
  child — not just defensible in the abstract.
- The new `ai-decision-support` `ConsentPurpose` row (applied in this
  session, one per school) is what tells a parent this processing happens
  at all, before any explanation feature answers *how*. `ConsentPurpose` and
  `ConsentRecord`/`DataSubjectRequest` already existed and are working (9
  purposes, 85 records) — this is one more purpose in an existing system,
  not a new consent mechanism.

## What every AI output already carries

Every row in `AgentAuditEntry` is, structurally, an explanation waiting to
be rendered:

| Column | Answers |
|---|---|
| `agentType` / `skillId` | Which of the five agents, and which of the eight specific skills, produced this |
| `skillVersion` | Which exact prompt/instruction set — resolvable to an `AgentSkillVersion` row once INTEGRATION.md's step 2 ships, showing the literal instructions and few-shot examples in force at the time |
| `inputRefs` | What the agent was given — lesson, student, resource IDs, not just a vague "context" |
| `standardsApplied` | Which curriculum/exam-spec standards it reasoned against |
| `outputSummary` / `decision` | What it actually recommended |
| `confidence` | Its own stated certainty |
| `reviewedById` / `reviewOutcome` / `reviewNote` | Who reviewed it, and whether they confirmed, overrode, or dismissed it — the human-in-the-loop record Article 22 cares about |
| `createdAt` / `reviewedAt` | When |

Nothing here needs inventing. What needs building is a view that assembles
these into a sentence a parent or inspector can read, and a query that walks
every entry for one student across their SEND journey rather than one at a
time.

## Two explanation surfaces

### 1. Per-decision explanation ("why did the AI suggest this")

Triggered from any point in the app that already shows an AI-suggested
output (a homework question, an ILP target, a resource adaptation). Renders
from a single `AgentAuditEntry` row plus its resolved `AgentSkillVersion`:

> **This suggestion was generated by Omnis's [agent name] on [date].**
> It used [standardsApplied, in plain language] and was based on [inputRefs,
> named — e.g. "this student's most recent K Plan and their last three
> ILP evidence entries"]. The system rated its own confidence at [X]%.
> It was reviewed by [reviewedById's name] on [reviewedAt], who
> [confirmed it as-is / edited it before use / dismissed it].
> [If overridden: reviewNote, if the reviewer left one.]

This is close to a template query, not a generation task — deliberately, so
the explanation is always traceable to the exact row rather than an LLM
re-narrating after the fact (an LLM-generated *explanation of a decision* is
itself a second thing that could be wrong; a rendered-from-data explanation
can't drift from what actually happened).

### 2. Student-journey explanation ("how has AI been involved in this child's support")

The one explicitly asked for — "how student AI was managed throughout their
learning journey." This is a `WHERE studentId = ?` sweep across
`AgentAuditEntry`, grouped and summarised:

- Total AI-assisted touchpoints, broken down by agent/skill (e.g. "14
  ENGAGE recommendations, 6 SEND_DIFFERENTIATION adaptations, 3
  MARKING_CONSISTENCY reviews")
- Review outcome breakdown (confirmed / overridden / dismissed counts) —
  this is the strongest single fact for demonstrating human oversight
  wasn't nominal
- A chronological timeline entry per `AgentAuditEntry`, using the
  per-decision template above, filterable by date range or skill
- Which `ConsentPurpose` rows are active for this student's school and
  whether an `ai-decision-support`-scoped `ConsentRecord` exists for this
  specific student where the school's consent model is per-pupil rather
  than per-school-blanket

This is the artefact a DSAR response, an Ofsted/SEND inspection request, or
a parent meeting can be built from directly — a full accounting rather than
a sample.

## What this deliberately does not claim

- It does not claim every AI suggestion is correct — it claims every one is
  traceable and was reviewed by a person. Those are different guarantees;
  conflating them would overstate what the system does.
- It does not use an LLM to generate the explanation text from scratch for
  the reasons above (traceability) — the *plain-language standards name* and
  *input description* fields can be template-filled from existing lookup
  tables (standards already have human-readable names elsewhere in the
  schema; this just reuses them), not freshly generated per view.
- It is not a new consent mechanism — it rides on the existing
  `ConsentPurpose`/`ConsentRecord` system, adding one purpose to it.

## Build scope (not yet built — this is the spec, not the code)

1. A server action, `getStudentAiJourney(studentId)`, doing the grouped
   `AgentAuditEntry` sweep above, schoolId-scoped like every other query in
   the app.
2. A `StudentAiJourney` view/component — reasonable to place as a tab
   alongside the existing student profile tabs (K Plan, ILP, evidence),
   consistent with how those are already organised — rendering the summary
   counts and the timeline.
3. A per-decision explanation renderer (`AiDecisionExplanation`), used both
   inline (wherever a suggestion is shown) and inside the journey timeline.
4. A DSAR export: reuse `getStudentAiJourney`, render to PDF alongside
   whatever the existing `DataSubjectRequest` export flow already produces
   for other data categories.

None of this requires the DSPy work to ship first — `AgentSkillVersion`
resolution (item 2 in INTEGRATION.md) makes the explanation richer
("here is the exact instruction text in force"), but the explanation surface
works today against `skillVersion: 0` / hardcoded-prompt state too.

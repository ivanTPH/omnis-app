# Omnis — resilience audit (2026-08-27)

First pass of the resilience thread of the post-launch hardening phase (per Ivan's "start with resilience" choice, opened right after the deployment incident during the security-sweep deploy — see `docs/audit/2026-08-27-hardening-security-sweep.md`'s "Deployment incident" section for that specific story). Scope: error handling and failure modes across the four nightly agent crons (`coach`, `quality`, `plan-synthesis`, `engage`), the DSPy weekly optimizer, the Oak/Wonde external syncs, and the e2e/deploy architecture that caused today's incident.

## STATUS: 6 findings fixed, committed `f99e715`. One architectural question (the e2e/production coupling) documented but deliberately not decided unilaterally — needs Ivan's call.

## Fixed

1. **CRITICAL — `lib/oak-delta-sync.ts` could mass-delete the entire Oak curriculum catalogue on a single bad HTTP response.** `getLessonEntries()` fetched the Oak sitemap with no `res.ok` check and no retry — unlike `fetchJson()` two lines below in the same file, which already does both. A transient Oak-side error (a 5xx, an HTML error page instead of XML, a timeout) would silently produce an empty entries list. `runDeltaSync()`'s reconciliation logic treats "not in the seen set" as "no longer exists" and soft-deletes accordingly (`updateMany({ where: { slug: { notIn: [...seen] } } })` for subjects, units, and lessons) — with an empty seen set, every row in all three tables (10,000+ `OakLesson` rows per the DSPy docs) gets `deletedAt` set in one run. Fixed two ways: the sitemap fetch now checks `res.ok` and retries 3x with backoff, matching the existing `fetchJson()` pattern; and a new `MIN_EXPECTED_LESSON_ENTRIES = 1000` floor aborts the sync before any reconciliation step runs if the entries list looks implausibly small, for any reason — this is a defense against the failure mode itself (a "200 OK but garbage content" response would defeat the fetch-level fix alone). Only affects the no-`OAK_API_KEY` fallback path; the primary bulk-sync path (`lib/oak-bulk-sync.ts`, used when `OAK_API_KEY` is set) has no delete/reconcile step at all, so this specific risk doesn't apply there.

2. **HIGH — `dspy-service/weekly_run.py` had two unprotected writes right after its one protected step.** The per-`(agentType, skillId)`-pair loop already isolated `optimize_skill()` failures correctly (try/except, logged, `continue`s to the next pair). But `data.write_skill_version(...)` — called immediately after, right after a potentially long MIPROv2 compile — sat outside that protection. A DB blip there crashed the whole process, abandoning every remaining pair even though only one write failed. Separately, the final `data.finish_optimization_run(...)` call was also unprotected; a failure there left the `AgentOptimizationRun` row stuck at `status='running'` forever, indistinguishable from "still executing" to anyone checking run history days later. Both are now wrapped the same way `optimize_skill()` already was — write failures are recorded per-pair and the loop continues; a failure on the final status write is logged to stderr (so the GitHub Actions job shows red) and the script now always exits non-zero in that case.

3. **HIGH — all four agent cron routes returned HTTP 200 even on total systemic failure.** Each route already isolates per-student/per-school failures correctly (`Promise.allSettled`-equivalent loops with try/catch per item) — a bad student never took down the batch. But if *every* call failed the same way (the clearest case: `ANTHROPIC_API_KEY` revoked or rotated, hitting every single Anthropic call in every agent), the routes still returned `200` with the failure count buried in the JSON response body. `.github/workflows/crons-agents.yml` invokes these with `curl -sf`, which only inspects the HTTP status — never the body — so a total outage could silently stop all four nightly agents indefinitely with no alert of any kind, matching exactly the "why hasn't this student's plan been reviewed in three weeks" scenario. All four routes (`agent-coach`, `agent-quality`, `agent-plan-synthesis`, `agent-engage`) now return `502` when `processed === 0 && errors > 0` — something was attempted and every attempt failed — so the cron step actually fails visibly in GitHub Actions instead of silently succeeding.

4. **MEDIUM — `agent-coach`'s `CRON_SECRET` check was inconsistent with its three siblings, and insecure by default.** `agent-quality`, `agent-plan-synthesis`, and `agent-engage` all deny any request when `CRON_SECRET` is unset (`if (!secret || ...) return 401`). `agent-coach` alone treated an unset secret as "dev mode, allow unauthenticated" — meaning if that env var were ever missing in production (not migrated during a redeploy, rotated in only three of four places), `agent-coach` would become a wide-open endpoint anyone could hit to trigger real LLM spend and write real `AgentAuditEntry` rows, while its three siblings would correctly go dark. Fixed to match the deny-by-default pattern the other three already use.

5. **MEDIUM — `lib/wonde-sync.ts`'s `inBatches()` helper let one bad record abort the rest of its phase.** It ran `Promise.all` over chunks of 10 items; a single upsert failure (a constraint violation on one employee/student/class record) rejected the whole chunk, which propagated up to that phase's try/catch and aborted every *remaining* chunk in that phase too — while earlier chunks' writes had already committed (nothing here is wrapped in a `prisma.$transaction`). Concretely: employee #245 of 500 fails → employees 250-500 are silently skipped for the run, 1-240 persist, and the only trace is one generic error string for the whole "Employees" phase. `inBatches()` now uses `Promise.allSettled` — a failed item is logged and skipped, and the batch keeps going through every remaining chunk. Per-item error messages currently only reach `console.error`, not `WondeSyncResult.errors` (which still gets one message per *phase*, not per item) — flagged below as a smaller follow-up if finer-grained error visibility is wanted.

## Not fixed — needs Ivan's decision, not a unilateral code change

**The e2e.yml / production coupling that caused today's earlier deployment incident.** `.github/workflows/e2e.yml` runs on every push to `main`: it triggers the Coolify deploy, waits 7 minutes, then hits `https://omnis.education` directly (both over HTTP and via a second, independent Prisma connection using the production `DATABASE_URL` secret) to warm auth and run the full Playwright suite. `connection_limit=20` (raised from 5 earlier today, see the hardening-sweep doc) is headroom, not a structural fix — a genuine production traffic spike coinciding with an E2E run could reproduce the same connection-pool cascade that failed two deploys today.

Investigated what's actually available before proposing anything:

- **A second Vercel project already exists** and auto-deploys from this same GitHub repo via Vercel's native GitHub integration (confirmed in `docs/audit/2026-08-26-schoolid-tenant-scoping-audit.md:9`; no workflow file deploys to it, so it's invisible to `.github/workflows/`). `CLAUDE.md` says "Vercel removed" as of 2026-08-12, which appears to mean removed as the *production target*, not that the project itself was deleted — the more recent 2026-08-26 audit says it's still deploying. This was not independently re-verified against the Vercel dashboard this round.
- `playwright.config.ts` already reads its target from `PLAYWRIGHT_BASE_URL` with no hardcoded fallback to production — pointing E2E somewhere else is a one-line change in `e2e.yml` (`PLAYWRIGHT_BASE_URL: https://omnis.education` → wherever), not a config rewrite.
- **10 of the 39 E2E spec files connect to Prisma directly** and perform real writes, independent of whatever URL Playwright's browser traffic targets — a second, separate source of DB load and mutation regardless of where the HTTP layer points.
- Tests target a demo tenant by fixture-email convention (`@omnisdemo.school`/etc.) — but `School.isDemo` (added earlier this session for the DSPy pipeline) is not referenced anywhere in `e2e/`, so this is a naming convention, not an enforced guard, and the demo school lives in the same production DB and connection pool as every real school.
- No staging Coolify environment or Supabase branch exists today — `evidence/phase6-load-resilience/failure-test-plan.md` explicitly names "Vercel preview + Supabase branch" as something that would need to be *built*, not something already in place.

Three real options exist, each with a real tradeoff, which is exactly why this isn't being decided without Ivan:
1. **Point E2E at the existing Vercel project instead of production** — cheapest if that project is actually healthy and current, but unverified this round, and the 10 DB-writing specs would still hit *some* real database either way (whichever one Vercel's deployment uses).
2. **Decouple the E2E trigger from the deploy trigger** — stop racing a full test run against the exact moment a new container is starting up under real traffic, without necessarily changing what E2E targets.
3. **Give the E2E job's own `DATABASE_URL` connection a separate, smaller pool** allocation so it can never contend with the app's own runtime traffic even if it does hit production.

None of these were implemented this round.

## Smaller follow-ups noted, not actioned

- `lib/wonde-sync.ts`: per-item failures inside `inBatches()` now go to `console.error` but aren't aggregated into `WondeSyncResult.errors` (which stays one message per phase). Fine for now since the phase no longer aborts, but a future pass could thread an error-collector through if finer-grained visibility into exactly which records failed becomes useful.
- `lib/wonde-client.ts`'s `wondeFetch()`/`wondeAll()` have no retry/backoff on transient API errors (429s, timeouts), unlike Oak's delta-sync (`fetchJson()`, 3x retry) — a single blip discards an entire fetched-but-not-yet-upserted page. Lower urgency since nothing had been upserted from that page yet (no half-written state), but still means a transient Wonde-side hiccup skips an entire resource category for the run rather than retrying.
- Both Oak sync paths and the Wonde sync have a 5-minute client-side timeout (`crons-agents.yml`'s `--max-time 310` for oak-sync; the four agent crons have no client-side timeout at all) against `maxDuration = 300` route configs, with no resumption/checkpointing if a real run needs longer than that — plausible for Wonde syncing many schools, or Oak's ~11,000 sequential-ish HTTP calls in the delta path. Not addressed this round; would mean redesigning these as resumable/paginated jobs rather than single long-running requests, a bigger change than this pass's scope.

## Confirmed handled well (reviewed, no changes needed)

- Batch isolation in all four agent crons was already correct at the per-student/per-school level before this round — only the *systemic*-failure visibility gap (finding #3) needed fixing.
- `plan-synthesis.ts` already wraps its Anthropic call + JSON parse with a fallback (`buildFallbackFromPreChecks`); `coach.ts`/`quality.ts`/`engage.ts` don't have the same explicit wrapping inside their per-student calls, but batch-level `Promise.allSettled` still contains the blast radius to one student, not the whole run.
- The dirty-flag design in `lib/agents/snapshot.ts` (`saveSnapshot` only clears `dirtyAt` after a full successful run) makes cron re-runs naturally idempotent — a killed/partial run can't lose track of what still needs doing.
- Both Oak sync paths and the Wonde sync are idempotent by design (every write is an `upsert` keyed on a stable external id), so a re-run after a partial failure doesn't duplicate records.
- `app/api/wonde/sync/route.ts` proactively marks any stale `'running'` sync-log row as `'failed'` before starting a new run, preventing indefinite "running" ghosts in that table (though it doesn't alert anyone in the meantime).
- DSPy's per-pair optimization already had correct isolation, graceful skip-on-insufficient-data (checked twice), and a real DB trail distinguishing "no candidate beat baseline this week" from "crashed" — only the two unprotected writes (finding #2) needed fixing.

## Wonde/curriculum data scope, resource-sync narrowing, and "deeper insights" enrichment — review
### 2 September 2026

Three related questions about how far Wonde/Oak sync and AI personalisation should reach. Checked against the actual code and Wonde's public API docs rather than assumed.

---

## 1. Does Wonde provide curriculum/exam board data? No — confirmed both ways.

Checked Wonde's own API documentation directly: it exposes students, employees, classes, attendance, achievements/behaviour, internal assessment records, contacts, subjects (as a label) and timetables/lessons — but no exam board, curriculum specification, qualification framework, or syllabus data anywhere in the API. Wonde is a roster/MIS mirror, not a curriculum authority — no MIS integration (SIMS, Arbor, Bromcom) works any differently here, this is true of the category, not a Wonde-specific gap.

Confirmed the same from the other direction: `lib/wonde-client.ts` and `lib/wonde-sync.ts` — the actual code that talks to Wonde — never reference exam board, curriculum, or syllabus anywhere. Nothing is lost or missing; there was never a Wonde field for this.

**The good news: you already built the right answer for this, it's just underused.** There's a `SubjectConfig` model (school admin sets a default exam board + tier per subject, `/admin/subjects` UI, propagates down to `SchoolClass.examBoard` for classes that don't have their own override) plus a `updateClassExamBoard` action for HOD/SLT/SCHOOL_ADMIN to override at class level. This is exactly "use the app dashboard to set curriculum/exam board alignment" — it exists today.

**The gap:** it's not part of the school onboarding wizard (`/admin/onboarding` — profile, invite staff, connect MIS, done — no exam board step), so a new school can go live with every `SubjectConfig.examBoard` sitting `null`, and nothing prompts them to fill it in. The feature is real but easy to miss. Worth a 5th onboarding step, or at minimum a dismissible banner on `/admin/subjects` for any core GCSE/A-level subject with no exam board set.

## 2. Should the resource sync be narrowed to a school's actual exam board? Mostly yes, but at the right layer.

Two different things are happening under "sync," worth separating:

**The Oak content ingest is shared across the whole platform, not per-school** — it's a weekly cron (`npm run oak:delta`, Sunday 02:00 UTC) that pulls Oak's full library once for every school on Omnis, not once per customer. Narrowing *that* to "only AQA" would be wrong — a different school signing up next month may run Edexcel, and the ingest needs to already have their content. So there's no unnecessary AQA-vs-Edexcel sync happening per school today, and narrowing the ingest itself isn't the fix. (Separately: when `OAK_API_KEY` is set it's an efficient bulk download; the "~11,000 calls" only applies to the fallback web-scraping path used when no API key is configured — worth checking that key is actually set in production, since that's a much bigger and slower load than it needs to be regardless of exam board.)

**Where narrowing genuinely should happen — and currently doesn't — is retrieval.** `findOakDataForTopics()` in `lib/oak-content.ts`, the function that picks which Oak lessons feed into AI homework/lesson generation, filters only by subject and free-text topic match. It never looks at `OakLesson.examBoard` at all, despite that field existing, being indexed, and the school's actual exam board already being knowable from `SubjectConfig`. So right now, a school running Edexcel can get AQA-flavoured lesson content pulled into its AI-generated homework with no board-awareness whatsoever — that's a real relevance gap, not a performance one, and it's the more important of the two to fix. For KS3 (years 7–9) this doesn't matter much — exam boards aren't relevant pre-GCSE — but for KS4/KS5 subjects it does.

**Recommendation:** filter/prioritise `findOakDataForTopics()` by the class's (falling back to the school's `SubjectConfig`) exam board for KS4/KS5 subjects only, with a graceful fallback to board-agnostic results when nothing's configured (given the onboarding gap above, plenty of schools won't have it set for a while). This improves relevance, and as a genuine side benefit, a smaller and more targeted candidate set means less content injected into each AI generation call — lower token cost, not just better matches.

## 3. Sentiment analysis, geographic/personal enrichment for "predictive screening" — recommend against, and here's the reasoning rather than just the verdict.

Taking the two parts separately, because they're different risk profiles:

**"Should Wonde data improve sentiment analysis"** — Wonde doesn't carry anything sentiment-shaped (no free text, no emotional signal) — its behaviour/attendance/achievement records are already exactly what feeds the existing evidence-based concern-flagging (`SendConcern`, `EarlyWarningFlag`), which is the right way to use that data: real recorded events, not inference. If "sentiment analysis" means something further — inferring a child's emotional or mental state from their writing, messages, or behaviour patterns — that's a materially different and much higher-risk feature, and I'd recommend against building it as an automated system. Automated emotional-state inference on children's data is exactly the kind of thing that drifts into mental-health-adjacent territory (false positives are not a neutral cost when the output could shape how a child is treated at school), and it's the sort of feature that needs a DPO and probably a clinician's input before a single line of code, not after. If there's a genuine safeguarding gap you're trying to close, the answer is very likely "make it easier for a human to flag a concern and get it reviewed quickly" (which is what's already built) rather than "have the system infer distress on its own."

**Geographic/demographic enrichment for "predictive screening, personalisation and deeper insights"** — recommend against this one clearly, for three compounding reasons:
1. **Postcode/geographic data is a well-known proxy for protected characteristics** — deprivation, ethnicity mix, disability prevalence all correlate with area-level data. A model that uses geography to "predict" SEND needs or attainment isn't adding insight, it's adding a systematic way to under- or over-flag children based on where they live, which is exactly the failure mode the ICO's Children's Code (Standard 10, Profiling) singles out — profiling children is discouraged by default, and only justified when it's demonstrably in the child's best interest with real safeguards, not as a "richer dataset" convenience.
2. **It cuts against data minimisation** (UK GDPR Art. 5(1)(c) — collect only what's necessary for the purpose) and it isn't necessary: the product's actual value, and the whole basis for the Ofsted Inclusion Evidence Report we just built, is that Omnis identifies need from *real evidence* — a raised concern, a graded homework pattern, a teacher's observation — not from demographic inference. Adding proxy data doesn't make that stronger, it undermines it.
3. **It's a genuine positioning risk, not just a compliance one.** The product's differentiator right now is "individual, evidence-backed, not profiling by category" — that's the story in the Ofsted report, the "My Support Plan" page's non-stigmatising framing, all of it. A predictive layer built on postcode data is the opposite of that story, and if it ever became visible (a DSAR, a journalist, a parent asking "why was my child flagged"), it would be very hard to defend as anything other than exactly the kind of profiling the sector is trying to move away from.

**Suggested next step, if you want to close this out properly rather than just park it:** document that geographic/demographic enrichment for predictive screening was considered and explicitly not pursued, with the reasoning above — a "considered and rejected, here's why" note is itself good Children's Code practice (it shows the question was actually weighed), and it's a one-paragraph addition to the existing DPIA rather than new work. I'm not a lawyer or your DPO, and this is exactly the kind of call that should get a second, qualified opinion before it's fully closed — but my strong steer is: don't build this, and the reasoning above is what I'd want on record either way.
